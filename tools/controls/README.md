# Traffic controls: OSM + authoritative city data

`data/controls.*` holds every signal, stop sign, yield sign and ramp meter. The schema is in `data/roads.schema.md`,
under "Traffic control", and `src/sim/controls.js` reads it.

## Build

```
npm run build:controls     # = node tools/controls/build.mjs
```

1. `tools/build_controls.py` builds the OSM controls on the flat-ground world. Their committed output is
   `data/src/flat/controls.*`; `bash tools/osm/build_world.sh osm` rebuilds them from OSM.
2. `tools/controls/merge.py` merges the authoritative datasets and writes `data/controls.{bin,json,meta.json}`.
   It also writes the coverage report `tools/controls/report/merge-report.json`.
3. `tools/elevation/patch_points.mjs data` sets each control's `y` from the road heights.
4. `tools/build_junctions.mjs data/` moves junction stop lines to the junction mouths, builds crosswalk legs
   and writes `data/junctions.bin`.
5. `tools/lines/build_lines.mjs data` writes the lane markings (`data/lines*.bin`).
6. The build gzips `data/controls.json` to `data/controls.json.gz` and runs `npm run verify:world` (sha256 vs
   `tools/osm/world-manifest.json`).

`node tools/controls/build.mjs --osm-only` skips the merge. It reproduces the original OSM-only world
bit-identically: `node tools/osm/verify.mjs --baseline osm-only`.

## Datasets (`sources.json`, pinned in `sources.lock.json`)

The lock file records each dataset's download date, feature count and the sha256 of the normalised GeoJSON.
`npm run fetch:controls` re-downloads the datasets; `node tools/controls/fetch.mjs --check` only reports
drift.

| San Francisco | SFMTA stop signs, DataSF `4542-gpa3` (one record per sign, with the direction it faces) | ODC PDDL 1.0 | **merge** (snapshot committed) |

| Oakland | City of Oakland GIS TrafficSignals | none stated | verify only |
| South San Francisco | Traffic_Signals_View | none stated | verify only |

Verify-only datasets are never written into `data/` and never committed. `fetch.mjs` stores them in
`data/controls-src/verify/`, which is gitignored. Their gaps are listed as `knownMissing` in the report, not
added.

No authoritative open data was found for:
- Palo Alto, Sunnyvale, Santa Clara, Redwood City, San Mateo, Menlo Park, Burlingame, San Bruno, Millbrae
- Daly City, Belmont, San Carlos, Foster City, Los Altos, Milpitas
- Fremont, Newark, Union City, Hayward, San Leandro, Alameda, Berkeley

Caltrans publishes no GIS layer of state-highway signals or ramp meters, only a PDF map and the Ramp Metering
Development Plan.

## Merge rules (`merge.py` docstring)

- **Signals:**
  - An authoritative signal within 40 m of an OSM junction signal confirms it.
  - An unmatched one is snapped to the nearest junction with at least 3 legs, within 30 m. Every
    non-motorway leg gets an approach, and the stop line is at the mouth. A stop or yield sign on that junction is replaced.
  - OSM signals missing from a city inventory are kept with `verified: false`, because inventories omit Caltrans and
    neighbouring-city signals.
- **SF stop signs:** each sign adds a stop on the leg whose heading matches the sign's facing direction, within
  50°. A junction becomes all-way when every leg (at least 3) has a stop. OSM stops that SFMTA's legislated list
  doesn't have, within 50 m, are removed, except on numbered state routes.

Every control records:
- `source`: `osm`, `osm+<dataset>` or `<dataset>`.
- `verified`:
  - `true`: matched to a merged dataset
  - `false`: inside a merged dataset's area but not in it
  - `null`: no merged data covers that place
- `authIds`.
- `timing: "synthetic"`, on signals and ramp meters.

## Timing is synthetic

No city publishes machine-readable signal timing; SFMTA timing cards need a public records request. Every plan
is generated by `src/sim/controls.js`:
- fixed time, with two approach axes
- protected lefts on big arterials
- ITE yellow of 3–5 s and a 1.5 s all-red
- a 60, 90 or 120 s cycle, with a green wave along the major axis
- ramp meters on a 6 s cycle from 06:00 to 10:00

There are no flashing or beacon states.

## Signal shape (optional renderer helper)

`src/look/signals.js` builds the signal heads, poles, mast arms and STOP/YIELD plates as three.js instanced meshes, all
from the approach geometry:
- They sit at the stop line and face the approach, with the pole 1.2 m right of the carriageway.
- The pole is 6.4 m and carries an arm over the lanes, an over-lane head and a pole head.
- The lamps follow `TrafficControls.stateOf`, so they show what the sim's drivers perceive.

**The shape is generic:** the same assembly everywhere, with no per-site head positions or mount types. The env never imports this file.
It needs `three`, either through `npm i three` or an import map in the page:

```html
<script type="importmap">{ "imports": { "three": "https://cdn.jsdelivr.net/npm/three@0.160.0/build/three.module.js" } }</script>
<script type="module">
  import { createSignals } from './src/look/signals.js';
  const U = { uViewportH: { value: innerHeight } };          // the only shared uniform it reads
  const signals = createSignals(U);
  scene.add(signals.group);
  await signals.attach({ controls: env.sim.controls });     // or { graph, pack } to build its own controller
  // per frame: signals.setTime(env.sim.time); signals.update(camera);
</script>
```

## Validation

- `npm run validate:controls` samples 24 intersections (seeded) from the SF, San Jose, Oakland, South SF and Mountain View
  records, plus SF stop intersections. It checks that the control is present, its approach count, and how far
  its stop lines are from the record. Output is in `tools/controls/report/validation.txt`.
- `bash tools/controls/spotcheck/fetch.sh && python3 -I tools/controls/spotcheck/compare.py` compares named
  intersections with live OSM through Overpass, one request at a time with back-off.
